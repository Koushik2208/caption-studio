- `@remotion/install-whisper-cpp`'s `transcribe()` threw "input file not found" for a perfectly valid, existing WAV path → `transcribe()` spawns whisper-cli with its `cwd` set to `whisperPath` (e.g. `tools/whisper/bin`), so a *relative* `inputPath` resolves against that cwd, not `process.cwd()` → always pass an absolute path (`path.resolve(...)`) for `inputPath` in server/index.ts
- `transcribe()` also threw "input file not found 'true'" when passing `splitOnWord: true` → the library builds whisper-cli's args as `['--split-on-word', splitOnWord]` (appends the raw boolean, not just the flag), and whisper-cli's `-sow` takes no value — it treats the stray `"true"` token as another input filename → whisper-cli 1.7.6 already defaults `-sow` to on, so just omit `splitOnWord` entirely instead of passing `true`

- Wiring `@remotion/player`'s `<Player>` with captions that arrive later from React state (ProjectContext, after transcription) needed less ceremony than expected, not more: `<Player>`'s `inputProps` is just a normal reactive prop, so when `captions` goes from `null` to a populated array, Player re-renders the composition with the new value automatically - no ref/imperative API needed, unlike updating things mid-playback (seeking, play/pause) which does go through PlayerRef. The one real gotcha was on the composition-component side: `CaptionRenderer`'s original design (copied from faceless-app) always calls `delayRender()`/`continueRender()` around a `fetch(staticFile(...))`, which is correct for that static-file async-load case but wrong for props Player already handed you synchronously - unconditionally delaying would just wait forever if nothing ever calls `continueRender` for the provided-props path. Fixed by only creating the delay handle when there's no `captions` prop to fall back on, so the same component serves both "fetch a static JSON file" (faceless-app) and "render whatever's already in memory" (Caption Studio) without a second component.
- `<Player>` requires a fixed numeric `durationInFrames` up front, but a freshly-uploaded media file's real length isn't known synchronously → reading it off a detached `<video>` element's `loadedmetadata` event works for audio-only files too (the `duration` property populates the same way), so one hook covers both media kinds instead of branching; a small fallback frame count covers the gap before metadata loads.
- `@remotion/renderer`'s `renderMedia()` also needs a fixed `durationInFrames` (via the `VideoConfig` returned by `selectComposition`), same problem as `<Player>` but server-side where there's no DOM `<video>` element to read metadata from → client already computes `durationInFrames` for the Player preview (`useMediaDurationFrames`), so it's simplest to just send that same number in the export POST body and read it back via the composition's `calculateMetadata({props}) => ({durationInFrames: props.durationInFrames ?? fallback})` — avoids re-deriving media duration server-side entirely.
- tsconfig.node.json uses `"module": "nodenext"`, which requires explicit file extensions on relative imports (`.js`, even though the source file is `.ts`) — server/index.ts importing a type from `../src/captions/styles/types` needed the `.js` suffix (`.../types.js`) to satisfy `tsc -b`, even though nothing is ever emitted (`noEmit: true`) and `tsx` resolves the real `.ts` file fine at runtime regardless of the specifier's extension.
- Any element that needs to render identically in both the browser `<Player>` preview and a headless-Chrome `renderMedia()` export (e.g. the Overlay tab's watermark) should avoid icon fonts/external `<link>`-loaded assets — the app's index.html font links aren't part of the separate webpack bundle `@remotion/bundler` builds from `src/remotion/index.ts`, so an icon that displays fine in the SPA preview could silently disappear (or render as a fallback glyph) in the actual exported file. Built `WatermarkOverlay`/`ProgressBarOverlay` with plain text/CSS shapes instead of `material-symbols-outlined` for this reason.
- `@remotion/renderer`'s `renderMedia({ scale })` multiplies the fixed `<Composition>` pixel size at render time rather than requiring a second composition per target resolution — confirmed via ffmpeg on real output: `scale: 1` on the 1080x1920 `CaptionExport` composition renders 1080x1920, `scale: 2` renders 2160x3840 exactly. This is what ExportPage's Resolution dropdown maps to (`src/export/resolutions.ts`), instead of needing separate `width`/`height` Compositions in Root.tsx for 1080p/4K/720p.
- `npx playwright install chromium` in this environment prints a "run npm install first" warning, but that warning is a red herring — a chromium build is already cached under `~/AppData/Local/ms-playwright/` on this machine (installed by some earlier tool), the warning just means `npx` can't resolve the local `playwright` npm package to drive it. Fix: `npm install playwright@<version matching npx playwright --version>` into a scratch dir (e.g. `npm init -y && npm install playwright@1.61.1 --no-save`), then run scripts from there importing `chromium` from that scratch `node_modules` — no need to touch the project's own `package.json`/`node_modules`. Superseded the earlier "treat live-browser verification as unavailable" guidance — it's available, it just needs the package installed somewhere on disk, not necessarily in the project.
- A Playwright script placed outside the scratch `node_modules` (e.g. directly in the scratchpad dir) throws `ERR_MODULE_NOT_FOUND: playwright` even though the package is installed — Node ESM resolves bare specifiers relative to the *importing file's* location, not `cwd`, so the script itself must live inside (or under) the scratch install dir, not just be invoked with that dir as `cwd`.
- Verifying Style tab changes end-to-end doesn't need real transcribed audio: `page.route('**/api/transcribe', ...)` can fulfill a fixed `{ captions: [...] }` JSON body directly, skipping Whisper/ffmpeg entirely — only a real (even silent) audio *file* is needed for the upload input and `<video>`/`<audio>` `loadedmetadata` duration read (`ffmpeg-static`'s bundled binary can generate one: `-f lavfi -i anullsrc=r=16000:cl=mono -t 4 out.wav`).
- Playwright's default `waitForSelector`/`locator` visibility wait times out (30s, no error until then) on inputs styled with Tailwind's `hidden` class (`display:none`) — this is intentional in the app (a real `<input type="file">` triggered by a styled button), not a bug to fix; use `{ state: 'attached' }` or just call `setInputFiles()` directly, which doesn't require visibility.
- Remotion's `<Player>` (this version, `@remotion/player` bundled with `remotion` 4.0.488) renders the composition inline into the host page's DOM, not into an `<iframe>` — a Playwright script inspecting rendered caption spans should query `page` directly rather than hunting for a content frame.
- Adding real Google Fonts (Bebas Neue, Archivo Black, etc.) as caption font presets can't rely on an index.html `<link>` tag like Inter/JetBrains Mono do — that only helps the SPA preview; the export bundle (`@remotion/bundler`/`renderMedia`'s headless Chrome) never sees index.html's `<head>`, so it would silently fall back to a system font on export while the live Player looked correct (same root cause as the icon-font entry above) → installed `@remotion/google-fonts` (pinned to the exact `remotion` version) and call `loadFont()` at presets.ts module scope instead; it calls `delayRender`/`continueRender` internally so both the Player and server-side render wait for the real font file. Verified specifically via a `renderStill` script through the actual export composition, not just the browser preview, since the export path was the one actually at risk.
- Playwright scripts that switch tabs to check state carried by React context (not localStorage) must use in-app navigation (`page.getByRole('link', ...).click()`), not `page.goto()` to a different route — `goto` is a full browser navigation/reload, which wipes in-memory state (uploaded media File object, live captions) that the app deliberately doesn't persist to localStorage; symptom looked like "captions don't render on Style tab" but was just the test losing state, not a product bug.
- OutlineDraw.tsx: a keyword-emphasized token (e.g. "bacteria") visually overlapped the next word on screen → `applyKeywordEmphasis`'s `scale` (1.15x) was applied via `transform: scale()` on the token's inline-block span, and CSS `transform` never reflows layout — the browser still reserved only the original (unscaled) box width, so the enlarged glyphs spilled into the neighboring token's box. Confirmed via `getBoundingClientRect`: the scaled span's box ended well before its rendered content did. Fixed by applying the keyword scale as a real `fontSize` bump (`FONT_SIZE * emphasis.scale`) instead of a transform — a real layout change, so the browser correctly reserves extra width and reflows the following token. Signature/SlideUp/Typewriter still use `transform: scale()` for their (animated, per-frame) pop-ins and could have the same latent bleed for a long keyword word — not fixed there since it wasn't reported and those animate every frame (a per-frame fontSize/reflow would be worse), but worth knowing if it comes up again.
- OutlineDraw.tsx: rendered text progressively drifted out of alignment across a sentence (word 1 fine, every word after worse) → the fill-sweep effect stacked two separately-rendered text nodes per token (an outline span + an absolutely-positioned fill-overlay span with the same text), and even after matching their `WebkitTextStroke` widths exactly, they still drifted — each span is an independent glyph render/antialiasing pass by the browser, so two copies of the "same" text are never guaranteed pixel-identical, and small sub-pixel differences compound token by token. Fixed by rendering exactly one element per token: `color: transparent` + `WebkitTextFillColor: transparent` + a gradient + `WebkitBackgroundClip/backgroundClip: 'text'` for the sweep, with `WebkitTextStroke` drawing the white outline on that same element. General rule: any progressive-fill-over-outline text effect should use single-element gradient-clip, never two overlaid text nodes trying to stay in sync. Superseded by the next entry (the gradient property itself needed a fix too).
- OutlineDraw.tsx (single-element gradient-clip version above): the currently-sweeping token rendered as a solid rectangle instead of gradient-filled letter shapes (only the *active* token broke; already-finished and not-yet-started tokens looked fine) → the animated gradient was assigned via the `background` shorthand (`background: linear-gradient(...)`), and re-assigning the `background` shorthand on any frame silently resets sibling longhands like `background-clip`/`-webkit-background-clip` back to their initial `border-box`, even though nothing touched those properties directly. This only breaks the active token because React's per-frame re-render only rewrites a DOM style property when its *value* changed since last frame - `backgroundClip`'s value ("text") never changes frame to frame so React stops re-applying it after frame 1, while the active token's `background` gradient string changes every frame (fillProgress interpolating) so React keeps rewriting it, and each rewrite re-clobbers the clip back to border-box with nothing left to restore it. Confirmed with an isolated repro: `el.style.background = gradient` on a 2nd write resets `getComputedStyle(el).backgroundClip` to `border-box` even when `background-clip:text` was never reassigned. Fix: use the `backgroundImage` longhand instead of `background` for the animated value - longhands don't reset sibling properties, so `backgroundClip` stays "text" indefinitely. General rule: never drive a per-frame-changing CSS value through a shorthand property (`background`, `font`, `border`, etc.) if a sibling longhand it silently resets (`background-clip`, `background-origin`, ...) needs to stay fixed across renders - use the specific longhand instead.
