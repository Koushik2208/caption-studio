Post-ship fix (same phase, user-reported): a keyword-emphasized word (e.g. "bacteria") visually overlapped the next word on screen. Root cause was `transform: scale()` on the token span for keyword emphasis - transforms don't reflow, so the browser kept the original (unscaled) box width while the glyphs rendered larger, bleeding into the next token. Fixed by applying the keyword scale as a real `fontSize` bump instead (inherited by the inner fill-overlay span, so outline/fill stay aligned) - a real layout change, so the browser now correctly reserves extra width. Confirmed via `getBoundingClientRect` measurements before/after (pre-fix: scaled box visually overlapped the next token's box by ~15px; post-fix: boxes touch exactly edge-to-edge, 0 overlap) and a live screenshot. See LEARNINGS.md for the full root-cause note, including that Signature/SlideUp/Typewriter share the same `transform: scale()` keyword-emphasis mechanism and could have the same latent issue for long keyword words (not fixed there - unreported, and their scale is animated per-frame so a fontSize-based fix isn't a drop-in replacement).

Follow-up investigation (same fix, user reported it still overlapping on "PUT THOSE TOGETHER"): re-tested exhaustively against the current code - single isolated keyword next to a non-keyword, two adjacent keywords with short words ("bacteria"/"chemistry"), and the exact reported words ("those"/"together" temporarily added to DEFAULT_KEYWORDS to match) all rendered with zero overlap (boxes touch exactly edge-to-edge in every `getBoundingClientRect` check and a live screenshot). Could not reproduce the overlap against the current fontSize-based fix in any variation tried - likely the screenshot was from a stale/pre-fix browser session (HMR didn't pick up the change, or an old export bundle cache per the existing node_modules/.cache LEARNINGS entry).
